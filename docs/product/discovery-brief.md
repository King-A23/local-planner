## 1. 一句话工作定义

**假设，不是已拍板：** 这是一款本机上的个人计划工具，帮助学生在同一处写下「今天要做什么」，并保住「还没做完、需要持续推进」的长期任务。

已知边界：

- 用户原话要的是「本地 todo 软件」，用途是每天制定计划，以及记录长期任务。
- 当前只做需求澄清，不进入实现。

待确认：产品名、第一版真正要赢的那一件日常、客户端形态、数据是否允许离开这台电脑。

## 2. 要解决的问题 vs 明确非目标

### 2.1 要解决的问题（工作假设）

以下问题来自用户目标、使用者和纸模线索，**不是用户已经确认的痛点**。

| 问题（假设） | 依据 | 状态 |
| --- | --- | --- |
| 同一天要同时面对课业、实验室、竞赛和多个代码项目，缺少一个「今天到底做什么」的落点 | 使用者身份与任务来源不单一 | 待确认是否为真痛点 |
| 长期任务容易丢，或挤不进「今天」 | 用户明确要求记录长期任务 | 已知有这个需求，痛的形态待确认 |
| 当天计划需要一个能一眼看完的日视图，而不是无限增长的总清单 | 本机有 Daily Planner 纸模 | 待确认纸模是否代表真实使用习惯 |
| 正经待办和买东西、交表、跑腿这类小事混在一起时，大事被淹没、小事也丢 | 纸模把 To-Do List 和 Quick Errands 分开 | 待确认是否要继承 |
| 有些天需要按小时看见自己的时间，而不只是一张勾选清单 | 纸模右侧是 06:00–23:00 Schedule | 待确认是否要小时排程 |

**待确认的关键未知：** 用户现在实际用什么记任务，以及它最让人受不了的一点。没有这个答案，上面每一条都只是假设。

### 2.2 建议 v1 先不碰的非目标

下列不是已拍板的产品决策，而是发现阶段建议先排除的范围，避免把「个人日计划 + 长期任务」做成大而全的生产力套件。

建议 v1 **先不碰**：

- 多人协作、共享清单、评论、指派
- 团队项目管理和甘特图
- 社交、积分、习惯打卡游戏化
- 用 AI 自动排一天、自动拆任务
- 完整日历替代（课程表导入、外部日历双向同步）
- 番茄钟 / 工时统计 / 周报月报
- 跨人提醒、邮件/短信通知体系
- 手机端作为第一版必达（形态本身待确认，但不宜默认做成多端产品）

仍可能进入后续版本、但现在不应驱动 v1 定义的：

- 多设备同步
- 提醒
- 与日历、课程表、GitHub、实验室工具联动

## 3. 两类工作负载，以及它们可能的关系

用户原话给出了两类工作，**没有给出它们如何连接**。下面只列选项，不选定。

### 3.1 当日计划

假设中的特征：

- 以「某一天」为边界，当天结束或下一天开始时，这份计划的主场景就变了
- 使用者要的是可执行的今天，而不是全部未完成事项
- 纸模暗示当天内部可能再分成：主待办、零碎差事、小时时间块

待确认：当日计划是一等对象（每天一张），还是只是「日期 = 今天」的过滤视图。

### 3.2 长期任务

假设中的特征：

- 跨过单日，做完之前都要能被找到
- 来源可能包括课业、实验室研究、竞赛、多个代码项目
- 不一定每天都要推进，但丢了会出事

待确认：长期任务是单独一类东西，还是「还没有排到某一天的任务」。

### 3.3 二者关系（选项，不选定）

| 选项 | 含义 | 对产品的影响 |
| --- | --- | --- |
| A. 完全分离 | 两个清单。用户自己把长期任务抄到当天 | 模型简单；重复录入和漏抄是代价 |
| B. 当天是投影 | 长期任务是主库，当天计划 = 从中挑出/分配到某日的子集 | 「记长期」和「做今天」是同一批对象的两种看法 |
| C. 可拆后排日 | 长期任务可拆成步骤，步骤才能排到某天 | 适合研究、竞赛、代码项目；v1 会变重 |
| D. 当天为主，长期为收件箱 | 先记下来，处理时才变成今天的一项，或继续留在 inbox | 捕获很快；inbox 可能堆积 |
| E. 项目为容器 | 课业/实验室/竞赛/代码项目装着任务；任务可无日期（长期）或有日期（当天） | 更接近多线工作，但先要承认「项目」是必要概念 |
| F. 接近纸模 | 每天一张独立日计划；长期任务是跨日仍未完成的累积，不自动出现在新的一天 | 日视图干净；结转规则必须另说 |

待确认：选哪一种，或第一版只做其中的最小切片。

## 4. 核心使用场景

以下场景都是工作假设，用来讨论产品该覆盖什么。每个场景是否进入 v1，待确认。

### 场景 1：晨间写下今天的计划

- **触发时机：** 新的一天开始，坐到书桌前准备安排今天。
- **用户动作：** 打开工具，看见今天的日期，写下或选出今天要做的事项。
- **成功标准：** 几分钟内得到一份当天能照着执行的清单，不必先翻完整条长期任务史。

### 场景 2：把突然出现的长期任务记下来

- **触发时机：** 课上、实验室、竞赛群或某个代码项目里，冒出一件几周后才截止、今天不必立刻做完的事。
- **用户动作：** 立刻记入长期任务，不强迫它出现在今天的计划里。
- **成功标准：** 这件事之后找得到、不会忘；今天的计划不会被它打乱。

### 场景 3：从长期任务里挑今天要推进的

- **触发时机：** 写日计划时，知道还有研究、竞赛或项目必须往前推。
- **用户动作：** 浏览长期任务（或某个项目下的任务），把其中几件放进今天。
- **成功标准：** 今天能看见要推进什么；没选中的长期任务仍在，不会因为没排今天就消失。

### 场景 4：同一天并行多条线

- **触发时机：** 这一天既有课业节点，又有实验、竞赛或代码项目。
- **用户动作：** 在同一份当天计划里写下/排入这些不同来源的事项。
- **成功标准：** 不需要在多个本子或应用之间切换，就能回答「今天要兼顾什么」。

### 场景 5：一天结束时处理没做完的

- **触发时机：** 当天结束，清单上仍有未勾项。
- **用户动作：** 区分已完成、放弃、挪到某天、送回长期任务。
- **成功标准：** 未完成事项有明确去处，既不会默默消失，也不会无规则地污染下一天。

### 场景 6：记下零碎差事，或把事情落到某个小时（待确认是否进 v1）

- **触发时机：** 冒出「去打印 / 交表 / 回一封短邮件」；或用户想按小时看见今天。
- **用户动作：** 把小事记到和主待办分开的位置；或把事项放到 06:00–23:00 的某个时间块。
- **成功标准：** 小事不丢、也不压过主待办；若使用时间块，用户能回答「今天下午是否还有空档」。

场景 6 直接来自纸模分区，**不代表用户已经要求软件照做**。

## 5. 对象模型草案（需要讨论的概念）

这里只列「可能需要有名字的东西」，不是数据表、字段或关系设计。每一个都可以被合并、改名或删掉。

| 概念 | 为什么可能存在 | 待讨论的问题 |
| --- | --- | --- |
| 日期 / 某一天 | 日计划几乎必然按天发生；纸模第一行就是 DATE | 它是过滤器，还是每天一张计划？ |
| 日计划 | 纸模是一页一天；用户原话有「每天制定计划」 | 是否为一等对象？有无「空的一天」？ |
| 任务 / 待办 | todo 软件的最小工作单元 | 完成状态怎么算？能否跨日？有无截止？ |
| 长期任务 | 用户原话单独提出 | 独立类型，还是「无日期 / 未排日」的任务？ |
| 零碎差事 | 纸模左侧下部独立于 To-Do List | 独立概念、任务标记，还是根本不要？ |
| 时间块 / 日程 | 纸模右侧 06:00–23:00 | 任务的另一种摆放，还是与待办无关的日历格？ |
| 项目 | 多个代码项目、实验室、竞赛都可能持续很久 | v1 要不要容器？没有项目，长期任务如何分组？ |
| 来源 / 领域 | 课业、实验室、竞赛、代码项目来源不单一 | 要分类，还是先一个扁平列表？ |
| 完成与未完成 | 计划软件几乎都要回答「做完没有」 | 只有勾选，还是允许部分推进、跳过、取消？ |
| 结转 | 软件相对纸张多出来的能力 | 未完成默认留在当天、跟到下一天，还是回到长期？ |

第一版不需要、也不应该先定：唯一 ID、层级深度、标签体系、优先级枚举、重复规则、附件、评论。

## 6. 和纸质 Daily Planner 的继承 / 差异假设

纸模事实（已知）：一页一天；页眉是日期；左栏 To-Do List，左栏下方 Quick Errands；右栏 Schedule，从 06:00 到 23:00 逐小时。

### 6.1 可能继承（假设）

- 以「今天这一页」为默认心智，而不是先进入一个巨大的总库
- 主待办和零碎差事在视觉上分开
- 若用户确实按小时过日子，右侧时间轴比纯清单更接近现有纸上动作
- 勾选完成，结构简单，不先上复杂状态机

### 6.2 软件相对纸张可能多出来的（假设）

- 纸张没有「长期任务库」；这正是用户原话多出来的那一半需求
- 未完成项可以结转、重排，而不必手抄到下一页
- 同一件长期任务可以在不同天被推进，而不复制成互不相认的几行
- 可以按项目或来源找回任务，纸张做不到
- 可以搜索、归档、回顾过去某一天

### 6.3 不要默认照搬的

- 软件不必做成「电子纸」；纸模是线索，不是线框定稿
- 小时表是否进入 v1：**待确认**（已知背景已写明暂不视为已定）
- Quick Errands 是否进入 v1：**待确认**
- 06:00–23:00 这个学生日程窗口是否适合每一天：**待确认**
- 纸模没有优先级、项目、截止日；不代表软件也不能有，只代表纸上日常可能不依赖它们

## 7. 需求分级

### P0 必须先澄清

没有这些答案，产品定义会漂。

1. v1 最想先解决哪一类日常：写今天计划、随时记待办、把长期任务拆/排到每天，还是按小时排程。
2. 现在实际用什么记任务，最受不了的一点是什么。
3. 当日计划和长期任务选哪一种关系（见第 3.3 节选项），或 v1 只做其中最小切片。
4. 纸模三块（To-Do List / Quick Errands / Schedule）哪些要进第一版，哪些只是纸上习惯。
5. 「本地」对用户的底线：数据绝不能离开这台电脑，还是只表示个人使用、同步可后说。
6. 一天结束未完成的事项，默认应怎样处理。

### P1 可后置，不阻塞第一轮定义

- 项目 / 来源分组是否必要
- 截止日期、优先级、标签的完整体系
- 提醒、通知
- 多设备、手机查看
- 与日历、课程表或其他工具联动
- 回顾、统计、归档浏览
- 长期任务是否允许拆步骤

### 明确不要过早设计的部分

现阶段不要设计、不要选型、不要画成方案的：

- 客户端技术栈、框架、是否 Web/原生/终端的实现路径
- 存储格式、数据库、文件布局
- 同步协议、备份策略的实现
- 通知系统、日历协议、导入导出格式
- 字段级数据模型、API、界面线框和视觉规范
- 任何里程碑式的实现计划或架构图

这些要等 P0 澄清之后再进入设计文档阶段。

## 8. 建议的下一轮问题

按决策杠杆从高到低，最多 8 个。答完前几题，后面的选项会自然变少。

1. **第一版最想先解决哪一件日常？** 写今天计划 / 随时记一笔待办 / 把长期任务排进某天 / 按小时排程。（杠杆最高：直接决定 v1 主场景。）
2. **现在用什么记这些事？最受不了的一点是什么？**（没有竞品痛点，无法判断软件该赢在哪。）
3. **长期任务和当天计划怎么连？** 分开抄写 / 当天是长期任务的投影 / 先拆再排日 / 长期当收件箱 / 先按项目装着 / 继续接近纸模的一页一天。（决定对象模型，而不是界面皮。）
4. **纸模上的 To-Do List、Quick Errands、06:00–23:00 Schedule，第一版要留下哪几块？**（决定日视图的复杂度。）
5. **一天没做完的事项，你希望默认去哪？** 留在当天 / 跟到下一天 / 回到长期任务 / 每次问你。（决定日与日之间会不会互相污染。）
6. **课业、实验室、竞赛、多个代码项目，第一版就要分开看，还是先一个扁平列表？**（决定要不要引入「项目/来源」。）
7. **「本地」的底线是什么？** 数据不能离开这台电脑 / 可以用本机文件或 iCloud 这类用户可控同步 / 多设备以后再说。（决定信任边界，仍不是技术选型。）
8. **第一版希望怎么打开它？** 本机网页 / macOS 桌面 / 终端 / 也要能在手机上看。（对实现影响大，但对「要解决什么问题」的杠杆低于前几题。）
